Asset & Work-Order Data Structure

A reusable data model for equipment and the outstanding work against it — the shared "skeleton" an infrastructure operator, security provider, or field-service organization can adopt to make unavailable resources and pending tasks visible, without commissioning a new system.

Demonstration schema & data — adapt the fields to your organization; replace the examples with your authorized records.

The two entities

An asset is a piece of equipment; a work order is a task against an asset. One asset has many work orders.

asset 1 ──< work_order many  ·  linked by asset_id

assets

One row per physical asset.

FieldTypeReq.Description / domain
asset_idtextrequiredStable unique identifier. One id per asset, forever.
tagtextrequiredField/asset tag following a naming convention (e.g. VEH-NP-01).
asset_typetextrequiredCategory (vehicle, pump, radio, panel, generator…).
sitetextrequiredLocation the asset belongs to.
statusenumrequiredin_service · maintenance · out_of_service
ownertextoptionalPerson/team accountable for the asset.
commissioneddateoptionalIn-service date (for age / life-cycle).

work_orders

One row per task. Every work order must resolve to an existing asset_id.

FieldTypeReq.Description / domain
wo_idtextrequiredUnique work-order identifier.
asset_idtextrequiredForeign key → assets.asset_id.
descriptiontextrequiredWhat needs to be done.
priorityenumoptionallow · normal · high · urgent
openeddaterequiredWhen the task was raised.
duedateoptionalTarget date; past + not closed ⇒ overdue.
closedboolrequiredtrue/false. Open work orders drive the "outstanding work" view.
closed_ondateoptionalCompletion date (if closed).

Derived, never entered by hand: an asset is available when status = in_service and it has no open work order flagged down; a work order is overdue when due < today AND closed = false.
